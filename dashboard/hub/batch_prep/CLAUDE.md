### Prep-day engine [BINDING]

`create_prep_day(recipe_ids)` walks the BOM over `recipe_ingredients.produces_recipe_id` and builds a **ground-up** step list — **raw → build-up → assemble** — persisted in `prep_day*` (+ per-step composition in `prep_day_step_component`, + the method in `prep_day_step.note`) so the checklist survives a phone refresh. The plan reads like building each batch from scratch **in the cards' own units** (Phase C-v2.1, 2026-06-05 — Sam: "you're not including all the steps… and you're gram-converting everything"):

- **raw** — every smallest part gathered first, ONE combined line per name: all juices **and** raw dry/wet goods (sugar, milk, spirits, sugar cane). **Preps are made as whole card batches**, so a prep's hidden raws are pooled in at full-batch size (one batch per distinct prep). Original units, summed independently per unit (R1).
- **build-up** — each needed sub-recipe reproduces its **full card recipe verbatim** (every ingredient's original `amount` text + the `method` line). No bare "make X". **Ordered by brew-time priority (Phase C-v5, 2026-06-06 — Sam: "things that need time to brew come first, longest first"):** sort key `(-depth, -lead_minutes, name)` — dependency depth still primary (an input prep is made before the prep it feeds), then **longest passive wait first** within a depth level, name last. Each step carries a plain-text `lead_label` ("infuse overnight", "sous vide 24 hr", "steep 10 min") rendered on its own indented line under the step name, in accent/blue (no chip) — aligned with the composition sub-list + method note below it (moved off the title row 2026-06-06 so it never crowds a long step name horizontally). See the lead-time rule below.
- **assemble** — each selected batch shown WITH its full card pull-together + method, plus an **earliest-completion ETA** (Phase C-v6, 2026-06-06): the parallel-brews critical path through the batch's preps — the longest dependency chain of brew times, assuming brews run at once — rendered as `earliest ready ~12 hr` in the same `lead_label` text slot (its own line under the step name; no brew gate → no ETA). `db.py` `_critical_path(conn, rid, lead_map, cache)` (max over prep children of `lead(child) + critical_path(child)`, memoised, cycle-guarded) + `_humanize_eta(minutes)` (<60→min, <24h→`~N hr`, <1wk→`~N day(s)`, else `~N week(s)`); excludes active assembly time. **Reuses the `prep_day_step.lead_label` column** — on a build-up step it's the brew wait, on an assemble step it's the ETA — so no migration. See the lead-time rule below.

Hard rules the engine honors:

- **Original units, never gram-converted.** The cards' juices are stored in **quarts**, sugars/waters in **oz**, spirits in **ml** (re-stored 2026-06-05 from the earlier gram values — see below); the build-up/assemble composition shows the verbatim `amount` text. This **realigns with the locked "don't assume quart→grams" rule**: the quart↔gram conversion is unknown until Sam weighs a quart on a real batch.
- **Layout: name left, every quantity right (Phase C-v2.2, 2026-06-06).** A raw step's `label` is the **name only** (`lemon juice`) — never a unit. ALL quantities sit on the right: `qty_g` is the gram part (drives the g/oz chip), `qty_extra` is the non-gram units summed per unit + joined (`2 quarts`, `18 bottles`, `8 oz + 2 quart`). Same-named raws **collapse into one line** (the engine aggregates by lowercased name; count nouns pluralise via `_plural`). `_combine_units` returns `(qty_g, qty_extra, label)`.
- **Raw order: fresh → stable (Sam, 2026-06-06).** The raw stage is sorted by prep order, **alpha within each tier**: tier 0 fresh (juices + produce + herbs), 1 pantry (dry/canned/shelf-stable non-alcohol — incl. teas, coffee, coconut milk, **condensed + evaporated milk**), 2 alcohol (every spirit, liqueur, wine, beer, bitters, **n/a spirit**), 3 refrigerated (cold-stored, added last — dairy + eggs **+ fresh-pressed sugarcane juice**; Sam 2026-06-06: dairy and sugarcane only, all other juices stay tier 0 Fresh). **The fridge tier sits LAST despite spoiling** — it's grabbed at the end of a build, kept cold until then (NOT strict perishability). The raw stage is reordered by tier; **build-up is reordered by brew-time priority** (`(-depth, -lead_minutes, name)` — see the build-up bullet above and the lead-time rule below); assemble stays per selection. Neither freshness nor brew time can break a make-the-cordial-before-the-drink dependency chain — depth stays primary in both.
  - **Classification is reasoned, stored as data — not keyword-matched (Phase C-v2.4, 2026-06-06).** The earlier substring classifier (`_ALC`/`_FRESH`/`_PANTRY_FORM`/`_ALC_WORD` keyword sets + word-boundary guards in `_perish_rank`) is **gone** — it silently bucketed anything it didn't recognise into pantry and needed a manual keyword for every miss (`Mijienta`, `verte`…). Each distinct raw ingredient is now **judged individually** and stored in the STRICT `ingredient_tier(name, tier, note)` table (migration 008, seeded by `seed_ingredient_tiers.py` — a reviewable per-ingredient dict, re-run to correct a row). `db.py` reads it: `_load_tier_map(conn)` → `{lower(name): tier}`; `_tier_of(name, map)` looks up case-insensitively and degrades an unknown name to pantry (`_DEFAULT_TIER = 1`); `missing_tiers()` returns raw ingredient names in recipes but absent from the table, so a newly added ingredient gets a deliberate classification instead of staying silently pantry. `_TIER_LABEL` maps the int tier to the `Fresh`/`Pantry`/`Alcohol`/`Refrigerated` header. The table is **data** (175 rows), editable per-row. Unlinked sub-recipes that leak into raw (`Batch (…)`, `L1:/L2:/L3:` layers, `citrus cordial (…)`) are parked in pantry with a `note` flagging the BOM-link gap.
  - **Tier is surfaced, not just sorted (Phase C-v2.3, 2026-06-06).** `get_active_prep_day` attaches a `tier` field to each **raw** step — the human label via `_TIER_LABEL[_tier_of(label, tier_map)]`; non-raw steps carry `tier: None`. Computed on read, **not persisted** (the raw step's `label` IS the bare ingredient name, so the table lookup reproduces the build-time tier — no stored column). The frontend (`batch.jsx` `PrepSteps`) emits a second-level `.tier-head` sub-header per tier within the raw phase, reset at each phase boundary. So the fresh→stable ordering reads as labelled groups, not an unexplained sequence.
- **Units never cross (R1).** A name needed in grams AND another unit is ONE collapsed line summing each independently — grams in `qty_g`, the rest in `qty_extra`. Never convert across units.
- **Composition rows carry the card text, not grams.** `_recipe_card(rid)` returns `(components, method)`; each component is `{name, qty_g:None, unit:None, label:<amount text>}` (made sub-recipes show the produced recipe's name). The g/oz toggle drives only the raw-stage gram chips, not these lines.
- **Cordial/prep ingredient re-store (2026-06-05).** Citrus Cordial (14) juices → `quart` (was the assumed 1892.7 g), sugar → `oz`; Simple Syrup (1), Jasmine Green Tea (17), Oolong Tequila (37) had `qty`/`unit` populated in original units (oz/ml). This **supersedes the earlier "quantify the cordial in grams + pool it" approach** (29.5735 g/oz, 6624.5 g yield) — that was a quart→gram assumption the new rule forbids. To bring another prep into the raw stage, populate its ingredient `qty`/`unit` in original units the same way.
- **Brew-time lead is reasoned data, stored per prep (Phase C-v5, 2026-06-06).** `recipes.lead_minutes` (passive wait until usable, the sort key) + `recipes.lead_label` (display text) are seeded by `seed_prep_lead.py` — a re-runnable per-prep dict keyed by lowercased name (migration 010). "Lead time" = time-until-usable driven by **passive unattended waits** (infuse/steep/rest/chill/freeze/dehydrate/sous-vide); active simmering counts only when there's no passive wait. **Card-stated** where the method gives a time (overnight→720, `sous vide 24 hr`→1440, `dehydrate 12 hr`→720, `sit 3 hr`→180, `steep 10 min`→10, Jackfruit's `sit 1 week`→10080 = the longest); **web-researched** (row carries a `RESEARCHED:` note) where the card says "make ahead"/"freeze"/"refrigerate" with no time (cold foams `chill ~2 hr`, yogurt `freeze ~4 hr`, Che Ba Mau jello `set ~3 hr`). `db.py` `_load_lead_map(conn)` → `{id: (minutes, label)}` drives the build-up sort; the label is stamped onto each build-up step's `prep_day_step.lead_label` at build time (snapshot, survives refresh). Edit a value in the seed and re-run to correct a row. Design contract: `docs/archive/specs/2026-06-06-prep-day-brew-priority-design.md`.
- **One active day at a time** — `create_prep_day` clears any open day before opening a new one; the active day is the latest `prep_day` row with `cleared IS NULL`. Components cascade-delete with their step, which cascades with the day.

### Structured storage map (Phase D, revived 2026-06-20)

The Map view is no longer a free-text `<textarea>` over `storage_note` — Sam: "rework the batch prep storage map into a proper ui, rather than unformatted text in a box." It is a **four-level editable tree** (migration 015): `storage_area` (room) → `storage_unit` (fixture; the collapsible card) → `storage_section` (shelf/row) → `storage_item`. The blob was irregular, so two passthrough conventions keep the tree uniform while rendering exactly like the old map: a **blank-named** (`''`) unit models items sitting directly under a room (Alcohol room, Notes), and a blank-named section models items under a fixture with no shelf (Left fridge's loose "Sugar cane juice in bag"). The frontend draws blank-named nodes without a sub-header but still lets you name them. `sort_order` is explicit at every level (physical order is meaningful — top row above bottom row); reorder is a sort_order swap with the adjacent same-parent sibling (the up/down arrows).

- **db.py** layer: `get_storage_tree()` (four ordered queries assembled in Python) + generic CRUD over the four levels via the `_LEVELS` whitelist — `add_node` / `rename_node` / `delete_node` (children cascade via FK) / `move_node` (up/down) — plus `set_item_note` and `reparent_item` (move an item to another section). Every mutation returns the whole tree under `{"tree": ...}`; adds also return `{"new_id": ...}`.
- **api.py** endpoints (all under the `{status: ok|error}` envelope): `GET /api/batch/storage/tree`; `POST/PUT/DELETE /api/batch/storage/<kind>[/<id>]` where `<kind>` ∈ area|unit|section|item; `POST /api/batch/storage/<kind>/<id>/move` (`{direction}`); `PUT /api/batch/storage/item/<id>/note`; `POST /api/batch/storage/item/<id>/reparent` (`{section_id}`). The legacy textual `GET/PUT /api/batch/storage` stays as the archive blob.
- **Frontend** (`jc.html`'s `#panel-map` + `batch.css` and the batch JSX): collapsible unit cards (count chip in the head) with item **chips** grouped under shelf sub-headers, matching the prep view's `.phase-head`/`.tier-head`/chip language. An **edit** toggle reveals inline `▲▼` reorder · `✎` rename · `✕` delete · `+` add at every level; item edits (rename · note · move-to-shelf · delete) use a small action-menu popover. DOM is built with `createElement`/`textContent` (no innerHTML), re-rendered from the authoritative tree each mutation returns.
- **Seed:** `seed_storage_map.py` is a one-time bootstrap that parses `storage_note` (`##` room / `###` fixture / `**bold**` shelf / `-` item, with bare `Foo:` lines as shelf labels) into the tree (5 areas · 12 units · 21 sections · 76 items). Guarded — refuses to clobber a non-empty tree unless `--seed --force`. `storage_note` (migration 003) is kept intact as the seed source + archive; the map view no longer reads it. Restore point: `data/work.db.bak-storage-tree-2026-06-20` (migration 015 is additive-only; its `-- +migrate down` drops the four tables).

### Prep-day picker (Phase C-v4, 2026-06-06)

The builder's recipe picker is a **two-tab, category-bucketed, collapsible** selector — not a flat chip wall (Sam: "doesnt just flood page with a bunch of chips"). **Drinks** (`kind=batch`) and **Preps** (`kind=prep`) tabs reuse the `.recipe-tabs`/`.recipe-search` shell; preps (syrups, cordials, infusions — 42 across 8 buckets) are now selectable alongside the 21 batches, so a prep day can be planned around making them too. Each tab groups recipes into **category buckets** (collapsible headers carrying a `selected / total` count), **collapsed by default**; a search box filters the active tab in place and force-expands matching buckets. A **selected tray** of removable chips sits above the build bar — selection (`state.prepSel`, keyed by recipe id → name) spans both tabs and survives collapse/search, so a collapsed bucket never hides a pick. The builder fetches both kinds (reusing the recipes-view `state.lists` cache); **no schema change, no new endpoint** — `list_recipes` already returns `category`, and `create_prep_day` already accepts any recipe ids. Directly selecting a prep with no drink yields a valid plan; the engine labels it under **assemble** ("assemble Citrus Cordial") rather than "make" — a known cosmetic quirk, deliberately not re-architected here. Design contract: `docs/archive/specs/2026-06-06-prep-day-picker-redesign-design.md`.

### Staged additions — a full queue (Phase C-v7, 2026-06-06)

You can **add** drinks or preps to the *active* day without resetting and reselecting (Sam: "add items if I forgot … but it doesn't mess up the original plan. I can make human judgment on when I can jump in"). A prep day is now an ordered series of **stages**: stage 0 is the original plan; each "add" appends the next stage (1, 2, …) as a **self-contained `raw → build-up → assemble` block pooled + brew-ordered within itself**, placed after every existing step and checkable immediately. Existing steps keep their `seq`, quantities, and `checked` state untouched — progress is preserved by construction. This is a **full queue**: the user decides by eye when to jump over and start the queued work; the engine never interleaves or re-pools across stages. Migration 011 adds `stage INTEGER NOT NULL DEFAULT 0` to `prep_day_step` + `prep_day_selection` (default 0 → every pre-existing row is the original plan). `db.add_to_prep_day(recipe_ids)` finds the active day, computes `next_stage = max(stage)+1` / `next_seq = max(seq)+1`, and appends via the shared `_insert_steps` (also used by `create_prep_day` at stage 0); `get_active_prep_day` returns `stage` on every step **and** selection row. `POST /api/batch/prep-day/add` mirrors the create endpoint's validation. Frontend: an **"+ add"** button in the active head reopens the bucketed picker in *add mode* (`state.addMode` — button reads "add to prep day", a **cancel** returns to the active day, recipes already on the day render as greyed `.pick-chip.is-inplan` and can't be re-picked); the checklist draws a `.stage-head` divider (*"added — &lt;names&gt;"*) before each queued block, with phase/tier sub-headers restarting inside it; `#prepMeta` names only stage 0. **Two deliberate cuts:** (1) **no cross-stage dedup/re-pooling** — a queued drink that needs a prep the original already makes lists "make it" again as its own batch (reasoning about leftovers would touch an in-flight process); (2) **no repeat batches of the same recipe** — `add_to_prep_day` skips ids already in the day (selection PK is `(prep_day_id, recipe_id)`); a mixed pick drops the in-plan ids and adds the rest, and an all-in-plan add raises `already in this prep day`. Adding with no active day raises `no active prep day`. Design contract: `docs/archive/specs/2026-06-06-prep-day-staged-additions-design.md`. Tests: `test_prep_day.py` `run_staged_additions()` (8 assertions — append, stage/seq numbering, stage-0 byte-for-byte preserved, check survives, no-repeat, no-active).

## Units model [BINDING]

- Grams is the canonical stored unit; weighed ingredients carry `unit='g'`.
- g ↔ oz is a single fixed factor: **1 oz = 29.5735 g** (fluid-ounce-of-water basis), display-only, applied only to weighed rows. This matches the laminated recipe cards exactly — do NOT revert to 28.3495 unless Sam says the bar weighs on a true gram scale. Full rationale in the design doc's units section.
- Counts/containers (`bottle`, `can`, `bag`, `gallon`, `quart`, `ml`, `oz`, `each`, `tub`) and non-scalable text (`to taste`, `in batch`) sit outside the g/oz toggle. Quart is a container count, never converted to grams. **Prep recipes are stored in their card units** (cordial juices in `quart`, syrup/tea waters+sugars in `oz`, spirits in `ml`) so the prep-day plan shows what the card says — the g↔oz toggle only touches rows actually stored as `g` (batch-direct weighed ingredients). See the prep-day engine block above.
- **Never collapse an amount to one chosen number** — `qty` holds the value Sam named, every conversion stays in the `amount` parens (the standing detail-preservation rule, memory `feedback_never_lose_detail_conversions_in_parens`). Ratio recipes were resolved to concrete grams at one batch; there is **no `formula` column** — the scaling engine carries ratios like any other recipe.

## Scaling is client-side

Rescaling is a pure client-side function. **The only control is editing any one ingredient amount** → `factor = newValue / baseQty` (Phase C-v3, 2026-06-06 — Sam: "scale by one ingredient"). The old ¼/½/full/custom preset buttons were removed; a single "reset to full" affordance returns the recipe to `factor = 1`. The pure engine (`scaleAmount`/`factorFromEdit`/formatters) is unchanged and still unit-tested in `batch.scaling.test.js`. It never mutates stored data and has no endpoint. Base grams come from the API; the client does the math.

## Recipes area (two tabs, Phase C-v3 2026-06-06)

The Recipes view is **two top-level tabs**: **Drinks** (`kind=batch`) and **Preps** (`kind=prep`). The 25 `kind=cocktail` single-serve specs are deliberately **out of scope** — this surface is for what you batch, not single pours. Each tab is **grouped by category** (headers) with a **search box** that filters the active tab by name in place (no refetch). Tabs + search live in a sticky `#recipeControls` bar.

- **Sort: batch type, then alpha (Sam, 2026-06-06).** `renderList` sorts client-side by `category` (lowercased — the "batch type", e.g. Clarified Batch / HH Clarified Batch / House Batch / House Shot) then by `name` within each, and draws a `.cat-head` per group. The earlier "rows arrive alpha, group preserving arrival order" left the category groups in a non-deterministic order; the explicit comparator fixes it.
- **List rows** carry name + a meta line (yield + ingredient count) + a **prep-vs-direct tag** (`multi-step` when the recipe depends on sub-recipes you build first, else `direct`). These come from the enriched `list_recipes` payload: `yield_qty`/`yield_unit` + `ingredient_count` + `sub_count` (correlated subqueries; no schema change). Yield renders as kg when stored grams pass 1000 (exact ÷1000, not the forbidden quart→gram assumption).
- **Recipes open inline, accordion-style (Sam, 2026-06-06: "open from the listing itself, not bottom").** There is **no separate detail view** — the old `#recipeDetail` section + `‹ back` button are gone. Tapping a row expands its full recipe (meta · scaler · ingredients · method) into a `.recipe-panel` rendered directly under that row; opening another row collapses the first (one open at a time, tracked by `state.openId`/`state.openEls`; the chevron flips ›→▾). `renderPanel` builds the body and `renderIngredients` writes into the open panel's elements. The detail fetch (`GET /api/batch/recipe/<id>`) still runs once per open.
- **Detail rows** read name-left / quantity-right (matching the prep-day checklist). The gap is a **line-free `.leader` spacer** — the dotted connector leader was removed module-wide (Sam, 2026-06-06: "connector lines is too many lines"); the row divider borders carry the separation. `.leader` is still the shared element (recipe rows, prep-day step rows, composition rows) so alignment is consistent, just without the dots.
- **Sub-recipe ingredients expand inline** — a line that produces a prep (`produces_recipe_id`) is a tap-to-expand row that fetches `GET /api/batch/recipe/<id>` once and renders that prep's ingredients read-only underneath, at the prep's own card amounts (factor 1, not scaled by the parent). Method, if any, shows below.
- **Method** stays a collapsed `.method-box` at the bottom of the panel (unchanged).

Design contract: `docs/archive/specs/2026-06-06-jc-batch-recipes-area-redesign.md` (the separate-detail-view + dotted-leader specifics there are superseded by the inline-accordion + line-free changes above).

## API + envelope

Blueprint `bp`, `url_prefix="/batch"`. All JSON responses use the `{status: ok|error}` envelope per the dashboard code standards. Endpoint list (build phase) is in the design doc's API surface section.

## Access posture [BINDING]

Reach `/batch` over the **private tailnet** (Tailscale phone → PC), never Tailscale Funnel — Funnel exposes the whole 5002 port and would leak the jobs tracker (salary/company/interview data), the same reason `/share` halts on the trips side. PC/WSL host needs a one-time Windows portproxy (`Windows:5002 → <wsl-ip>:5002`) + firewall allow; the server already binds `0.0.0.0`.
