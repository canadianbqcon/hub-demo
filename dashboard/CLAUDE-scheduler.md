# Headless skill scheduler (dashboard companion)

Split out of `dashboard/CLAUDE.md` on 2026-11-10 (size ceiling). Load it for any work on `hub/scheduler.py`, `hub/scheduler-config.json` or a scheduled job.

`dashboard/hub/scheduler.py` fires vault skills on a schedule via `claude -p "/skill"`, run from the vault root as non-blocking background children. Started once from `app.py`'s `__main__` (not on import, so tests don't spawn the thread). Design: `docs/specs/2026-06-27-headless-skill-execution-scheduling-design.md`.

- **Data-driven, ships inert.** Schedule lives in `dashboard/hub/scheduler-config.json` (`{active_machine, jobs}`). It ships empty, so nothing fires until populated. Each job: `{skill, time ("HH:MM"), enabled, mode}` and, for an irreversible skill, `readonly_cred_profile`.
- **Single-writer.** Only the machine whose `socket.gethostname()` equals `active_machine` runs the schedule; a null `active_machine` means no machine runs it (safe default). Cross-machine overlap is handled by this discipline, not a synced lock (manual rare git sync defeats a lock; the sign-out race is auth-token-mediated, not vault-mediated).
- **Atomic overlap guard.** Before launching, `run_skill` acquires an exclusive `fcntl.flock` on `<vault>/.pending/scheduler.lock` (`LOCK_NB`). Failure → skip + log. This is an atomic acquire, deliberately not a `pgrep` check (which is check-then-act/TOCTOU). Lock is held for the child's lifetime, released on exit.
- **Irreversible skills are code-gated, not prompt-gated.** `/gmail` and `/ynab` do their external writes via Bash-run Python (Google API client, `ynab` module), so Claude Code's `--disallowedTools` cannot deny "the Gmail modify scope" — there is no such tool to deny, and denying `Bash` also breaks reading. The only enforceable draft-only boundary is read-only **credentials**. `_enforce_boundary` therefore **refuses** to launch any skill in `IRREVERSIBLE_SKILLS` unless the job names a `readonly_cred_profile` that exists on disk — the code-level enforcement of "no irreversible action unattended." Read-only skills run to completion.
- **Read-only Gmail mechanism (built; token mint pending).** `services.gmail_readonly()` builds a `gmail.readonly` service; `services.gmail()` returns it whenever `VAULT_HEADLESS_READONLY=1` (the scheduler sets this for irreversible skills), so a headless write 403s at the credential layer. The `/gmail` skill has a matching "Headless draft-only mode" (skips calendar/confirm/execute/tracking, writes a proposed-actions draft to `log/gmail-drafts/`). The token is minted by `~/.config/vault-api/mint_gmail_readonly.py` (needs a one-time Google Console redirect-URI add for `http://localhost:8765/` + a browser approve). **`/ynab` has no equivalent** — YNAB personal tokens are full-access (no read-only scope), so it needs a GET-only proxy and stays blocked.
- **LLM-free Python jobs (`PYTHON_JOBS`).** A job entry keyed `{job, time, enabled}` instead of `{skill, ...}` runs a plain Python function, never `claude -p`. They include `forge-rebake` (checks the live League patch and re-bakes the Item Set Forge three times per patch — see `hub/forge/CLAUDE-chrome.md`), and `shift-sync` (reads work shifts off Google Calendar → replaces the future rows of `earnings_scheduled_shifts`, which is what the earnings forecast prices against; repeated at several times of day so a newly posted shift lands the same day). Both go through `_locked_run`, so they take the same flock as `run_skill` and a raised exception becomes a `status: failed` record rather than a dead thread. They need no `_enforce_boundary` gate because they take no irreversible external action — the only writes are local SQLite/vault files. `book-sync`'s record says `error` when the SimpleFIN pull itself failed (nothing fetched) and `partial` only for a bank-side warning such as one broken bank login. The pull gives each new row an existing payee from its cleaned bank text (`simplefin.match_payee`: digits dropped, same text seen before on a payee'd row, else the longest payee name that opens it; ambiguous means none), and a checking outflow with payment wording that names exactly one open card (last 4, product word, or the issuer word when that issuer has one open account) becomes a transfer at once, its card side a placeholder the card's own posting later adopts. One exception to "LLM-free": `book-sync` (01:30, 13:00, 21:30, just after the banks refresh, each with a backup 2 hours later) runs `finances/autocat.py` after the SimpleFIN pull, which calls Haiku 5.5 over the Anthropic API (key `ANTHROPIC_API_KEY` in `dashboard/.env`) and auto-approves high-confidence categories except P2P outflows and rideshares (pending holds wait until they post); an undone auto-approval blocks that payee until three of his answers agree. It then runs `finances/memo_lane.py`, which fills a blank memo from a matching Gmail receipt only when five strict checks pass, else stores a draft that waits on the Automations page; when that receipt makes the category unmistakable and the row is still uncategorized, it also categorizes and approves it (a `finance-category` decision, same Undo and payee block as autocat). Two memos need no email: a deposit equal to one Juniper & Co paystub `net` in `earnings.db` gets `Juniper & Co paycheck (pay period <start>–<end>)`, and MTA/OMNY gets `Subway fare`. Its writes are still local book.db rows a human can re-categorize, so it stays outside `_enforce_boundary`; it can run a minute or two, holding the scheduler flock. `voice-memo` (every 5 minutes, own lock `.pending/voice-memo.lock`) runs `automations/voice_memo_lane.py`: one Sonnet call per new voice memo with /recap's rules, then code guards, then calendar create or same-day time fix, staged transaction, owed debt or inbox line, each a `voice-memo` decision with Undo on Automations (no Fix there); never deletes, sends, moves money, or touches all-day or recurring events; anything unclear waits in `voice_memo_wait` for /recap; an undone kind is blocked until three of his /recap answers agree. Spec `docs/specs/2026-10-20-voice-memo-lane-design.md` (vault). Adding a job means adding a function plus a `PYTHON_JOBS` entry; `_tick` dispatches off that dict, so there is no per-job branch.
- **06:00 is the standard slot for nonspecific sweeps.** Any recurring job that just sweeps for work — no reason to run at a particular hour — goes at `06:00`, so the whole overnight catch-up lands in one place and the day starts clean. `forge-rebake` is there. A job with a *real* time constraint keeps its own times: `shift-sync` runs six times through the day because a shift posted at noon should land the same afternoon, which is a requirement, not a preference.
- **06:00 and 18:00 is the standard pair for twice-a-day jobs** (his call, 2026-10-20). `file-sort` and `downloads-tidy` run there. Weekly jobs take a `"days": ["mon"]` key on a normal `HH:MM` slot (`branch-check`, Mondays 08:00). An hourly `"*:MM"` slot plus a `DUE_CHECKS` entry makes a retry window: `news-digest` is `*:00` and `digest_api.due()` allows 06:00 up to noon, stopping once a digest is saved.
- **Python jobs sharing a slot run in SEQUENCE, in one worker.** They all take the same exclusive flock, so dispatching them in parallel means one wins and the rest log `skipped: locked` — and since a slot matches only for its own minute and a skipped run is still a logged run, the losers get no second attempt that day. `_tick` collects the due Python jobs and runs them in order in a single thread. Nobody is waiting on an unattended sweep, so sequencing costs nothing and it scales to however many jobs share the standard hour. Regression-tested (`test_two_python_jobs_in_one_slot_both_run`, which fails on parallel dispatch).
- **No auto-retry.** A failed run logs `status: failed` and exits; the next scheduled slot is the next attempt. Run records append to `<vault>/log/scheduler-runs.jsonl`; restart-safe dedupe (`_already_ran`) prevents a re-fire of the same skill+slot+day across a service restart. Status is read by `GET /api/scheduler/status`.
- **No new dependency.** A stdlib daemon thread polling twice a minute, chosen over APScheduler/`schedule` to avoid a transitive-dep risk under the systemd service's minimal PATH.

Tests: `dashboard/hub/tests/test_scheduler.py` (boundary gate, flock overlap, lock release, no-retry, single-writer, dedupe, same-slot sequencing, forge rebake cadence). When changing the scheduler's safety behavior, update this section and the design spec in the same operation.
